1 · What is Bend?

Short answer: Bend is a programming language. It is not a framework or a library. It comes with a method for working with AI coding agents, and the language enforces that method.

Language ✅

Bend 2 was released on 17 Sep 2026 by Victor Taelin / Higher Order Company. It has Python-like syntax and is open source (Apache-2.0). It compiles to C, CUDA, Metal or JavaScript. Files end in .bend.

Method ✅

Humans write the rules that must never break (the laws). AI writes the code and a proof that the code obeys every law. A checker verifies the proof. If it fails, the change cannot merge.

Framework ❌

You don't plug Bend into Python or Java like a library. It cannot even be imported from Python yet. In our POC it ran as a separate small service that other code calls over HTTP.

A proof is not a test. A test says "it worked for these 50 examples". A proof says "it works for every possible input", the same way a maths proof covers every number, not only the ones you tried. For ProofDesk, that means every category, every confidence value from 0 to 4,294,967,295, every customer profile, and every possible set of tickets.
Technical detail: what makes this possible
  • Bend 2 has dependent types: a type can state a fact, such as "for every desk d, the tickets after a tick are all ok". A function that type-checks against that type is a proof. Lean and Rocq work the same way.
  • The type checker is the proof checker. The authors claim it is several orders of magnitude faster than other proof assistants, so an AI agent can re-check after every edit.
  • It has affine types (a value is used at most once), so there is no garbage collector. Numbers are only Nat, U32 and F32. There are no type classes and no macros.
  • Parallelism is automatic. Two independent calls such as a b = run(x) run(y) run on different cores with no thread code.

2 · What goes in, what comes out

There are two different "runs" to keep apart. The check happens when code changes: it answers "may this change merge?". The program runs in production: it answers "what should happen with this message?".

A · The check (at merge time)

InputWho writes it
LAWS.bend: the rulesHuman
SPEC.bend: definitions the rules use ("a person", "no offer")Human
Desk.bend: the actual codeAI
PROOF.bend: proofs of each lawAI

Output: All terms check. or an error naming the law that failed, with expected vs. got. It is a yes/no gate, like a CI check.

B · The program (at run time)

InputOutput
A message: category, classifier confidence, threadWho handles it: Bot / Agent / Specialist
A customer: opted-out, open complaint, KYC, propensityCross-sell offer, or "no offer"
The desk state + an event (message, retry, 1 hour passes)New desk state: tickets, escalations, replies

It is compiled to a normal fast program (C, CUDA or JS). Whatever input arrives, the output obeys the laws.

Which file extension holds the laws? Laws have no special extension. They are ordinary .bend files that use the law keyword. By convention they live in LAWS.bend, owned by humans, and the AI agent is told not to edit it. Here is a real law from our POC: 
law regulated_goes_to_human:
  for +cat: D.Category
  for conf: U32
  {S.implies(D.is_regulated(cat), S.is_human(D.route(cat, conf))) == True{} : Bool}
In words: for every category and every confidence value, if the category is regulated, the handler is a human.
Technical detail: all 5 laws of ProofDesk

5 · With Bend vs. without Bend

Without Bend, critical rules are protected by tests and code review. Both are useful, and both have blind spots that grow as AI writes more of the code.

SituationWithout Bend (tests + review)With Bend (laws + proofs)
An edge case nobody thought of (e.g. fraud at 99% confidence)Passes if no test sits on that exact inputBlocked: the proof covers every input
Off-by-one at a boundary (≤ vs <)Caught only if a test hits the exact boundaryBlocked (bug D)
AI agent makes 50 edits a dayReviewer fatigue; each diff "looks fine"Every edit re-checked in ~0.2 s, automatically
Reviewing what the rules areRead the code (226 lines of engine) and infer the rulesRead the laws and spec (82 lines), written in business terms
Normal business change (new threshold, new SLA)Tests that hard-code old values break and need editingPassed with zero proof edits (changes F and G)
Proving it to an auditor"We have 200 tests""This rule holds for every input, checked on every change"
Hidden design gapsFound in productionWriting the Law 4 proof exposed a gap no test had caught: an escalated ticket could stay with the bot
Wrong or weak ruleWrongStill wrong, and it now looks "proven". This happened to us (see section 7)

6 · How do we run it?

Bend runs on Linux and macOS only. On our Windows laptops, everything runs inside Docker. It needs Docker Desktop and about 5 minutes the first time.

One-time setup (Git Bash)

cd "Bend AI/poc"
docker build -t proofdesk-bend .

This installs Ubuntu, clang, Python, Node and Bend 2.0.25 (pinned).

The main demo: the merge gate

./run.sh sh gate.sh

It prints All terms check. for the real code, then shows 5 bugs REJECTED and 2 business changes PASSED.

Other commands

./run.sh bend proofdesk/PROOF.bend      # just the proof check
./run.sh bend proofdesk/main.bend       # demo: a morning at a bank's desk
./run.sh bend proofdesk/spotcheck.bend  # one concrete example per law
./run.sh sh service/demo.sh             # HTTP service + Python client

PowerShell instead of Git Bash

docker run --rm -v "${PWD}:/work" -w /work proofdesk-bend sh gate.sh
Break it yourself in 1 minute
  1. Open poc/proofdesk/Desk.bend and find def route.
  2. Under case Fraud{}:, change Specialist{} to Bot{}.
  3. Run ./run.sh bend proofdesk/PROOF.bend. It fails and shows what it expected and what the code gives.
  4. Change it back. It prints All terms check. again.
How the proof connects to the rest of our (Python) platform

The proven engine runs as a small HTTP service (a sidecar) on port 8787. The LLM drafts the reply, and before acting the orchestrator asks the sidecar "who may answer?", "may I add an offer?" and "what is the ticket state?". We measured about 0.36 ms per routing call and 1.1 ms per ingest call.

GET /route/<cat>/<conf>          → handler, regulated?
GET /offer/<opted_out>/<complaint>/<kyc>/<cat>/<propensity>
GET /ingest/<msg_id>/<thread>/<cat>/<conf>
GET /tick        GET /tickets

The URL parsing and JSON output in the sidecar are hand-written and not proven. Only the decisions are.

7 · How much easier does it make things? Does it really reduce complexity?

The honest answer: Bend reduces risk and review complexity for a small set of critical rules. It adds engineering complexity, and today most of that sits in the language's immaturity. The complexity moves somewhere else rather than disappearing.

5/5
bugs caught, each confirmed as a real violation
0.5
proof lines per code line in our POC (121 / 226). An external review saw ~3:1 on harder logic
3.1×
speed-up on 8 cores with zero thread code
1.6×
plain Python was faster than Bend on the same 1M messages

✅ Where complexity goes down

  • Reviewing critical rules: read 82 lines of laws and spec in business terms, not 226 lines of engine.
  • Trusting AI-written code: the agent can edit freely. The gate, not a tired reviewer, stops rule breaks.
  • Edge cases: boundaries, huge values and odd flag combinations are covered automatically.
  • Regression safety: each change is re-proven in under a second, and business retunes need no proof edits.
  • Parallelism: spreading work across cores needs no threads or locks.

⚠️ Where complexity goes up

  • Writing the right laws is hard. Our first Law 3 was too weak. It still "passed" with duplicate protection deleted. We caught it only with runtime spot-checks. A proof is only as good as the law.
  • A strict, unusual language: no if, values used once, no functions calling each other, strict ordering. AI agents cope, but most engineers would need training.
  • Missing basics: no HTTP, JSON, dates or stdin, so plumbing is hand-written.
  • Integration: no Python import, so it runs as a sidecar service. Linux/macOS only, so Docker on Windows.
  • Maturity: 5 days old at test time, and the README says "expect bugs". The compiler was largely AI-written and is not independently audited.

Net effect by type of work

Type of logicComplexity reduced?How much
Small, pure, high-stakes rules (routing, eligibility, limits, dedup)Yes
Orchestration / workflows with I/O around those rulesPartly
Whole applications, web / mobile, data pipelinesNo, it adds complexity

The bars are our judgement from the POC, not measurements.

Our verdict: explore later. Don't use it for client work today. Do adopt the practice now: write each accelerator's non-negotiable rules as explicit laws and check them with property-based tests (e.g. Hypothesis in Python). That gets most of the value on our current stack. If a client needs mathematically proven rules today, look at Dafny, which is mature and compiles to Python. Re-evaluate Bend around December 2026.

8 · How Bend can help across Gen AI use cases

Every Gen AI system has two kinds of logic. The probabilistic part (the LLM's text, a classifier's guess) can only be evaluated statistically, never proven. The rule-bound part (who may act, what is allowed, what must never happen twice) can be proven. Bend proves the rules around the model, never the model itself.

The pattern that repeats: let the model suggest, and let a small proven core decide what is allowed. The model can be wrong, but the guardrail provably can't be bypassed. This is the most valuable idea from Bend, and it can be used with other tools too (Dafny, Lean, or property-based tests).

9 · FAQ and glossary

Is Bend a method or a framework?

It is a language that enforces a method (human laws, AI code + proofs, a mechanical check). It is not a framework: you can't add it to a Python project as a dependency.

What extension is used to create laws?

.bend, the same as all Bend code. Laws are marked with the law keyword and by convention kept in LAWS.bend. Supporting definitions go in SPEC.bend and proofs in PROOF.bend.

Does Bend prove the LLM gives right answers?

No. It proves the deterministic rules that take the model's output as input. For example, "whatever category and confidence the classifier outputs, fraud never reaches the bot".

Who writes the proofs? Do our engineers need to?

In our POC, an AI agent (Claude) wrote all the code and proofs in one working session, with about 10 check-and-fix cycles of under 1 s each. Humans must still review the laws, which needs one engineer comfortable with functional programming and a compliance owner.

What does "proven" NOT cover?
  • That the laws are the right business rules. Humans must review them.
  • The HTTP/JSON plumbing, and anything with I/O.
  • The LLM and classifier outputs.
  • That the compiler turns proven source into a correct binary. That is why we cross-checked 1,048,576 messages against Python and got identical totals.
How much does it cost?

Nothing in licences: it is free, under Apache-2.0. The real costs are people (skills to review laws, proof upkeep on structural changes) and integration (sidecar, Docker).

What are the alternatives?

Dafny is mature, proves automatically and compiles to Python: the best choice today if a client needs proofs. Lean / Rocq are powerful but manual. SPARK/Ada is proven in industry. Property-based tests (Hypothesis) are not proofs, but they check laws on thousands of random inputs in our current stack.
